## 3. 665cde1 的架构与框架

### 3.1 技术与部署框架

- Python 3.12+、Hatchling 和 uv：`665cde1:backend/pyproject.toml`、`backend/uv.lock`。
- FastAPI、Uvicorn、LangGraph、Postgres/SQLite checkpoint、psycopg、sentence-transformers。
- 原生静态前端（HTML/CSS/JS），Caddy 负责静态托管、`/api/*` 反代和 SSE 刷新：`665cde1:frontend/{app.js,Caddyfile,Dockerfile}`。
- Compose 形态为 frontend + backend + PostgreSQL：`665cde1:deploy/docker-compose.yml`。

### 3.2 后端分层

```text
backend/src/app/
├─ api/v1/endpoints/       HTTP 路由、DTO、依赖注入
├─ services/               ChatService 等用例边界
├─ agents/assistant/       LangGraph、节点、状态、提示词与检索工具
├─ infrastructure/         模型客户端、checkpoint、线程存储
├─ core/                   Settings、日志、lifespan
└─ main.py                 create_app 组合根
```

`main.py:create_app()` 只组装 FastAPI、中间件、路由和异常映射；`core/lifespan.py:create_lifespan()` 统一创建/释放 checkpointer、`ThreadStore`、graph 和 `ChatService`。`api/v1/endpoints/chat.py` 保持为薄 HTTP 层，`services/chat_service.py` 负责会话归属、图调用和 SSE 事件。

### 3.3 旧链路与优点

```text
浏览器 → /api/v1/chat → ChatService → LangGraph
START → analyze_intent → retrieve_knowledge
      → (必要时一次 refine_query 重试) → generate_reply → END
      → SSE start / complete / error / end
```

其优点是协议层不直接调用模型或图，模型客户端可注入并受 Pydantic JSON schema 约束，业务会话元数据与 LangGraph checkpoint 分开管理，且测试按 unit/integration 划分。其局限是检索仍依赖进程内 JSON 索引、知识发布缺少原子版本切换和细粒度 trace。

## 4. 当前架构与已具备能力

### 4.1 当前模块边界

```text
frontend/                         静态聊天 UI 和 Caddy
backend/app/main.py               HTTP、SSE、配置、依赖装配、运行时初始化
backend/app/agents/assistant/     五节点 LangGraph 和回答安全
backend/app/knowledge/skill/       Skill 编译、校验、运行时渲染
backend/app/knowledge/ingestion/   Markdown 摄取、分块、元数据
backend/app/knowledge/retrieval/   FTS、向量、融合、rerank、证据判定
backend/app/knowledge/repositories/ Corpus/trace 发布与 PostgreSQL 访问

deploy/、scripts/、evaluation/     Compose、发布、回滚、评估
```

### 4.2 当前请求与知识链路

```text
浏览器 → Caddy → POST /api/v1/chat
  → ThreadStore 归属校验 + LangGraph checkpoint
  → build_context
  → analyze_scene_and_plan（Skill policy）
  → retrieve_evidence（FTS + pgvector → RRF → rerank → Evidence Gate）
  → generate_answer → validate_output → SSE complete
```

图顺序见 `backend/app/agents/assistant/graph.py`；节点实现在 `nodes.py`。生产启动会校验模型、Skill 和版本化 Corpus readiness；未就绪时 `/ready` 返回 503 并拒绝 chat：`backend/app/main.py`。`scripts/publish_corpus.py` 通过 staging、写入索引、关联关系和发布切换构建在线 Corpus；`CorpusPublisher` 保留一个 retired 版本用于回滚。

### 4.3 当前必须保留的优势

1. Skill 源与编译产物有哈希/语义校验：`backend/app/knowledge/skill/`。
2. 生产检索不是单一 JSON 索引，而是 FTS、pgvector、Weighted RRF、CrossEncoder、冲突抑制、多样性和预算控制：`backend/app/knowledge/retrieval/service.py`。
3. Evidence Gate 在证据不足时清空不可靠证据，避免把无关来源包装为依据：`evidence_gate.py`。
4. Corpus、来源 manifest、发布版本和 Retrieval Trace 可审计：`knowledge/governance/`、`repositories/`、`observability/`。
5. Compose 中由 `postgres healthy → corpus-publisher completed → backend healthy → frontend` 控制生产形态：`deploy/docker-compose.yml`。

## 6. 多 Subagent 审查与决策

本方案经过三个独立只读分析视角后收敛：

| 视角 | 结论 | 对方案的影响 |
|---|---|---|
| 旧提交架构提取 | 旧提交在 HTTP/service/infrastructure/core 分层、资源关闭、可注入模型客户端方面清晰；同时混入 IDE/运行期文件 | 只借鉴分层与生命周期，不复制目录或产物 |

分歧处理：旧实现的 `src/` 布局和 `pyproject.toml` 有助于工程可维护性，但对当前正在工作的检索链路进行目录级迁移，回滚和验证成本过高。因此将“恢复包元数据”列为 P2，将“全量目录迁移”明确排除在本方案之外。

## 7. 优化方案

### P0-1：受控启动与资源生命周期

**问题。** `backend/app/main.py` 在导入期读取环境、创建数据目录、连接 PostgreSQL、加载 embedding/reranker、进入 `PostgresSaver` context 并构建 graph。启动失败后会静态落入 unavailable/in-memory 分支，运行期不可恢复；资源关闭所有权也不集中。

**方案。** 引入不可变 `Settings`、`create_app(settings)` 和 lifespan/应用容器：将环境读取、模型/数据库/checkpointer/`ThreadStore` 创建移入 lifespan，把已就绪依赖挂到 `app.state` 或受限容器。`/ready` 从容器读取真实状态；关闭时显式退出 `PostgresSaver`、关闭连接/池和 `ThreadStore`。

**范围。** 新增 `core/config.py`、`core/lifespan.py`、`bootstrap/container.py`（名称可按现有约定微调）；收缩 `backend/app/main.py`。不改 `knowledge/` 内检索、Skill 或 Corpus 契约。

**验证与回滚。** 为 `create_app` 注入 fake 依赖；覆盖缺模型、缺 DB、冷启动 reranker、启动失败、shutdown 的测试；用 Compose 真 PG 跑 `/ready` smoke。以独立提交交付，保留原入口可快速回退。

### P0-2：消除跨会话全局串行

**问题。** 现有 `graph_lock` 包住完整 `graph.invoke`，包括同步模型调用和 reranker；任一慢会话会阻塞所有会话。

**方案。** 先建立按 `thread_id` 的 keyed lock registry：相同会话保持顺序，不同会话并行。`get_state`、delete 与 invoke 使用同一会话锁；若 checkpointer 并发约束不满足，则以该约束为依据调整服务层/连接池，而不盲目解除锁。

**验证与回滚。** 新增“同会话串行、不同会话并行、取消/超时”集成测试；以 10 个不同会话做吞吐/尾延迟对照。保守回滚方式是 feature flag 恢复全局锁。

### P1-1：恢复 API、应用服务与模型适配器边界

**方案。** 把 `ChatRequest`、设备 ID 校验、SSE formatter、404/503 映射移动至 API 层；引入 `ChatService` 承接会话 claim、graph 调用和线程读写；将 `call_json`/`model_payload` 移入模型 client。图仍注入当前的 `AssistantNodes` 与 `build_assistant_graph`，不得复制旧图的检索逻辑。

**验证。** 保持 `/api/v1/chat`、SSE 事件顺序、owner isolation 和错误状态码的外部契约；补 API 集成测试及无 FastAPI 启动的 `ChatService` 单测。

### P1-2：明确连接与持久化资源所有权

**方案。** 由容器统一管理连接池，为知识 repository、LangGraph checkpointer 和 thread store 分配受控连接/上下文，避免共享单个长生命周期连接跨请求使用。保留当前 PostgreSQL schema 和 Corpus 发布逻辑。

**验证。** shutdown 关闭测试、10 并发请求、PostgreSQL 重启后的 readiness 恢复测试。若池化改变事务边界，应先补 repository 契约测试再切换。

### P2：可复现构建与测试结构

**方案。** 恢复 `pyproject.toml`/锁文件、pytest/ruff 配置及 unit/api/integration 目录语义；先不迁移到 `src/` 布局，也不在同一批次改动检索算法。补最小 CI：编译/import、unit、可选真实 PostgreSQL profile。

**验证。** clean venv、Docker build、现有 `py -m unittest discover -s tests -v` 与新增分类测试均通过。当前本地 JSON 模式不等价于生产 Evidence Gate，不能把其结果当作生产质量证据。

## 8. 实施顺序与非目标

1. 先冻结当前 API、SSE、检索和 Corpus readiness 契约，并加 P0 所需测试。
2. 实施 P0-1，完成真实 Compose startup/shutdown 验证。
3. 实施 P0-2，确认同会话一致性和跨会话并发。
4. 实施 P1 的边界拆分和连接池化，每一步独立可回退。
5. 最后处理 P2 构建元数据与测试组织。

非目标：不回退到 cards/JSON 检索；不复制 `.idea` 或 `.langgraph_api`；不进行 `backend/src` 大迁移；不在本次优化中引入真实用户认证、token 级流式输出或前端框架重写。这三项可在容量/产品需求明确后单独立项。
